# agent-meshy-wrapper

Pure skill plugin — no binary of its own. It wraps the **official Meshy MCP server** ([meshy-dev/meshy-mcp-server](https://github.com/meshy-dev/meshy-mcp-server), MIT, npm `@meshy-ai/meshy-mcp-server`): the MCP is declared inline in the `mcpServers` block of **both** `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json`, and `skills/meshy-wrapper/SKILL.md` teaches the agent when and how to drive it. The host agent launches the server automatically via `npx`.

## Contracts an agent won't infer from the tree

- **The API key travels two different paths, and that asymmetry is deliberate.** Claude Code declares it as a `userConfig` option (`api_key`, `sensitive: true`, `required: true`) and substitutes `${user_config.api_key}` into the server's `env.MESHY_API_KEY`. Codex has no `userConfig` equivalent, so its manifest ships **no `env` block at all** and the server inherits `MESHY_API_KEY` from the launching process. Adding an `env` block to the Codex manifest to "fix the asymmetry" would either hardcode a secret into the repo or set the variable to an unexpanded literal — `lint.yml` fails the build if one appears. `${user_config.*}` is only expanded in MCP/LSP configs and hook `args`; it is rejected in shell-form commands, so the value must stay in `env`, never in `command`/`args`.
- **The key is never stored in the repository or in `settings.json`.** `sensitive: true` routes it to the OS keychain (or `~/.claude/.credentials.json`); only non-sensitive `userConfig` values land in `settings.json` under `pluginConfigs`. Note that Claude Code reads `pluginConfigs` **only** from user settings, `--settings`, and managed settings — a project's `.claude/settings.json` is ignored for this, so the key cannot be supplied per-repo.
- **Every tool call spends the user's money.** Meshy is credit-metered against the account behind the key (1 credit for a conversion, up to 36 for a Creative Lab run). This is why `SKILL.md` carries a Cost governance section rather than leaving spending to host-level permission gating: an approved tool call and an approved *charge* are not the same thing.
- **The server ships its own agent instructions, and `SKILL.md` deliberately does not duplicate them.** `dist/instructions.js` exports a ~130-line workflow guide (credit table plus scenario playbooks A–J: printing, game engine, character animation, AR, retexture, conversion, UV unwrap, Creative Lab) that the host injects as MCP server instructions on connect. `SKILL.md` covers only the layer around it — money, task lifecycle, download location, ecosystem handoff. If a future server version drops or rewrites that guide, `SKILL.md` becomes *incomplete*, not merely stale, and would need the scenario content moved in.
- **Downloads write into the session's working directory.** `meshy_download_model` saves to `{cwd}/meshy_output/` — in an agent session that is the user's repo, so generated binaries land in a worktree unless `save_to` is passed. `SKILL.md` requires warning the user and offering a `.gitignore` entry before the first download; that is not a server behaviour anyone can change from here.
- **The version pin is exact on purpose.** `@meshy-ai/meshy-mcp-server@0.4.0` in both manifests lets `npx` reuse one cached package instead of re-resolving against the registry — the same cold-start reasoning as `agent-serena-wrapper` and `agent-blender-wrapper`. Bumping it means editing both manifests **and** re-checking `SKILL.md`: the tool inventory (24 tools), the credit figures, and the documented constraints (rig ≤ 300k faces, UV unwrap ≤ 40k faces GLB, `meshy_get_task_status` 300 s wait cap, `CHARACTER_LIMIT` 25,000) are all read off a specific server version. `lint.yml` enforces that the two manifests never drift apart, but it cannot tell you the docs went stale.
- **`meshy_send_to_slicer` returns launch commands, it does not execute them.** Acting on its output means starting desktop software on the user's machine from an agent turn. `SKILL.md` requires surfacing the command for confirmation first; keep that requirement there rather than assuming host permission prompts cover it.
- **Release is orphan-branch + marketplace dispatch.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) stamps the version into both manifests, force-pushes an orphan `release` branch holding only install-ready files, and POSTs the same dispatch (`category: skill`, `tags: ["3d","creative","ai"]`) to BOTH `seretos-agents/modular-software-factory-staging` (lands straight to main, no review) and `seretos-agents/modular-software-factory` (opens a review PR there). `main` and `release` share no history. Clients install at the tag `agent-meshy-wrapper--vX.Y.Z`.
- **Required secret:** `MARKETPLACE_DISPATCH_TOKEN` — fine-grained PAT, `Contents: RW` + `Pull requests: RW` on both `seretos-agents/modular-software-factory` and `seretos-agents/modular-software-factory-staging`.
- **`assets/icon.png` and `description.md` are release artifacts, not just repo files.** The dispatch payload sends `raw.githubusercontent.com/${repo}/${TAG}/assets/icon.png` and `.../description.md`, so both must live on the orphan `release` branch at the tagged commit — `release.yml`'s stage step copies them in for exactly that reason. Ship a real icon before cutting v0.0.1 or the listing has no image.
- **Depending on an MCP plugin:** declare it under `dependencies` in `.claude-plugin/plugin.json` (`{ "name": "agent-<mcp>", "version": ">=0.0.1 <1.0.0" }`). The Meshy server is wired directly via `mcpServers` in both manifests (not via `dependencies`), which is why `dependencies` stays `[]`.
